# 0002: Speech-to-text engine and model

- **Status:** accepted
- **Date:** 2026-10-24
- **Ticket:** STU-49

## Context

After the wake word fires, the phone streams 16 kHz mono 16-bit PCM to the server. The voice loop's budget is under 1.5 s from end of speech to first reply audio, so STT should take under ~400 ms for a typical 3 s command on the RTX 3090. It also has to share the 24 GB card with the local LLMs (STU-48) and TTS (STU-50).

End of speech is detected on the phone (VAD, STU-69), so the server receives one complete utterance at a time.

## Decision

- **Engine:** [faster-whisper](https://github.com/SYSTRAN/faster-whisper) (CTranslate2) behind the `SpeechToText` protocol in `server/alfred_server/voice/stt.py`. The voice gateway depends only on the protocol, so a Parakeet-class engine can replace it later without touching callers.
- **Model:** `distil-large-v3` with compute type `int8_float16`. This is `ALFRED_STT_COMPUTE_TYPE=auto`, which picks `int8` on CPU.
- **Decoding:** greedy (`beam_size=1`), `language="en"`, no server-side VAD, no conditioning on previous text. Whisper has no en-GB language code, so British spelling can be nudged with `ALFRED_STT_INITIAL_PROMPT` if it turns out to matter.
- **Loading:** the model is loaded once per process (`get_stt()`), at startup when `ALFRED_STT_ENABLED=true`, and warmed up with one silent decode. At most `ALFRED_STT_MAX_CONCURRENCY` (1–2, default 1) transcriptions run at once. The model gets that many CTranslate2 workers (`num_workers`), so 2 really decodes in parallel rather than queueing inside CTranslate2. Decoding runs in a worker thread so the event loop stays free.
- **Length cap:** utterances longer than `ALFRED_STT_MAX_AUDIO_S` (default 30 s) are rejected with `AudioTooLongError` as soon as the buffer passes the limit. A stuck VAD or misbehaving client can't make the server buffer audio indefinitely or tie up the GPU.
- **No partial results for now.** Whisper isn't a streaming model, and with phone-side VAD the whole utterance takes ~130 ms to transcribe. Re-decoding a growing buffer for partials would cost GPU time for no latency gain. If partials are wanted later (e.g. live captions), add an optional method to the protocol.
- **CUDA libraries:** cuBLAS and cuDNN 9 come from the optional `cuda` extra (`uv sync --extra cuda`), registered at load time. CI and CPU-only installs skip them. A CUDA base image that already ships them also works.

## Benchmark

`server/scripts/bench_stt.py` measures latency end to end through `FasterWhisperSTT.transcribe`, with audio streamed in 20 ms chunks. Timing runs from the end of the stream to the transcript being returned, so it includes PCM conversion and any wait for a concurrency slot, not just decoding. The comparison table below was first recorded as decode time only. Re-running the chosen configuration end to end gave 112 / 118 ms (2.9 s clip) and 117 / 123 ms (3.6 s clip), the same within noise, so the comparison stands. Each figure is from 10 runs per clip after warm-up, on the RTX 3090 (driver 610.88, Windows 11), faster-whisper 1.2 / CTranslate2 4.8. The clips are the synthetic en-GB fixtures in `server/tests/fixtures/audio/`. Similarity is a word-sequence ratio against the expected text, and every model scores 0.91 on `timer.wav` only because it writes "10" for "ten".

| Model | Compute type | 2.9 s clip mean / p95 | 3.6 s clip mean / p95 | 6.4 s clip mean | STT VRAM |
| --- | --- | --- | --- | --- | --- |
| small.en | float16 | 68 / 74 ms | 94 / 175 ms | 114 ms | ~0.8 GB |
| **distil-large-v3** | **int8_float16** | **117 / 119 ms** | **131 / 158 ms** | **135 ms** | **~1.3 GB** |
| distil-large-v3 | float16 | 127 / 190 ms | 134 / 162 ms | 137 ms | ~2.2 GB |
| large-v3-turbo | float16 | 135 / 144 ms | 155 / 185 ms | 159 ms | ~2.4 GB |

All candidates are well inside the 400 ms target with the GPU otherwise idle. `small.en` is fastest, but the synthetic clips are too clean to separate the models on accuracy. distil-large-v3 is the large-v3 family's English distillation and is much more robust to real-world accents and noise than `small.en`, for ~50 ms more. int8_float16 matches float16 on speed and transcripts at ~60% of the memory.

**Two workers (`ALFRED_STT_MAX_CONCURRENCY=2`):** loaded and idle, the second CTranslate2 worker adds only ~50–100 MiB (~1.2 GB vs ~1.28 GB total for STT). Single-request latency is unchanged at 110 / 114 ms for the 2.9 s clip. Two jobs decoding at the same moment also need working memory for each. That peak hasn't been measured, so check `nvidia-smi` under real concurrent load before relying on 2.

### Alongside the LLMs

These were measured with the STU-48 Ollama container serving `gpt-oss:20b` (12 GB) and `qwen3:4b` (4 GB), both loaded:

- **VRAM:** all three models resident peaked at **~18.4 GB of 24 GB**. That's 12 + 4 GB for the LLMs, ~1.3 GB for STT, and ~1.1 GB for the Windows desktop. No OOM. That leaves ~5.5 GB for TTS (STU-50) and KV-cache growth.
- **Latency with the LLMs loaded but idle:** unchanged (2.9 s clip 118 ms mean).
- **Latency while `gpt-oss:20b` is generating at the same time:** 2.9 s clip 360 ms mean / 469 ms p95, 3.6 s clip 283 / 300 ms. GPU contention roughly triples STT latency. In the normal voice loop STT finishes before that request's LLM call starts, so this only applies when a background task (scheduler, another device) is generating. If that becomes common, options are to pause background generation during an utterance or use the smaller model.

To re-run:

```bash
cd server
uv sync --extra cuda
uv run python scripts/bench_stt.py --model distil-large-v3 --device cuda
```

## Consequences

- With the LLMs loaded, STT adds ~1.3 GB of VRAM and ~120–140 ms per utterance.
- The first start downloads the model (~1.5 GB) to the Hugging Face cache, or to `ALFRED_STT_DOWNLOAD_ROOT`. A container should mount that path as a volume.
- The fixtures are synthetic. Re-check accuracy with real recordings of Dan once the phone client (STU-65) can capture them, and revisit `small.en` vs distil-large-v3 then.
- The acceptance test runs `tiny.en` on CPU in CI (~75 MB download, cached). Point it at the production model locally with `STT_TEST_MODEL=distil-large-v3 STT_TEST_DEVICE=cuda uv run pytest -m model`.
