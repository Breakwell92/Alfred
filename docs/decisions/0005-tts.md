# 0005: Text-to-speech engines, streaming and output format

- **Status:** accepted
- **Date:** 2026-10-24
- **Ticket:** STU-50

(The ticket asked for `0003-tts.md`; 0003 was already taken by the local-models ADR, so this is 0005.)

## Context

Replies are spoken on the phone. To keep the voice loop under ~1.5 s from end of speech to first reply audio, speech has to start before the LLM has finished its reply. So TTS works sentence by sentence on the token stream, and the first sentence should be audible within ~250 ms. Personas (STU-66) will choose a voice, speed and pitch. The 3090 is shared with the LLMs and STT (ADR 0002, 0003), so VRAM use matters.

## Decision

- **Interface:** `TextToSpeech` in `server/alfred_server/voice/tts.py`: `synthesize(text_stream: AsyncIterator[str], voice: VoiceConfig) -> AsyncIterator[bytes]` (an async generator) and `voices()`. `VoiceConfig` is `engine` (`kokoro` | `piper`; `cloud` comes with the persona ticket), `voice` id, `speed` (0.5–2.0) and `pitch` (±6 semitones). The voice gateway (STU-64) depends only on this protocol.
- **Output format (for the gateway and Android):** mono, signed 16-bit little-endian PCM at **24 kHz**, whatever the engine, in chunks of at most 200 ms (9,600 bytes). Piper's 22.05 kHz is resampled with soxr. Each sentence or clause is followed by 100 ms of silence. `GET /voices` also reports `sample_rate`.
- **Sentence splitting:** `SentenceSplitter` buffers the token stream and emits a segment at `.`, `!`, `?`, `…` (with any closing quote or bracket) or a line break. To start audio sooner, the **first** segment is also cut at a clause (`,` `;` `:` or a spaced dash) once it has 4 words. A `.` doesn't end a sentence after a common abbreviation (Mr, Dr, St, e.g., vs…), an initial (J. R. R.), a list marker (`1.`), or when the next word starts lowercase (`5 p.m. tomorrow`). Decimals (`3.50`) never break because a boundary needs whitespace after the punctuation. Segments over 250 characters are cut at their last clause or space. The splitter waits for the word after a `.` before deciding, which costs one token.
- **Kokoro (default):** [kokoro-onnx](https://github.com/thewh1teagle/kokoro-onnx) with the fp32 `kokoro-v1.0.onnx` model and `voices-v1.0.bin` (54 voices). Default voice `bm_george` (British male). Runs on **CUDA** through onnxruntime-gpu: it's about 2x faster than the CPU for short sentences (table below), and only CUDA meets the 250 ms target. `ALFRED_TTS_KOKORO_DEVICE=auto` falls back to the CPU when CUDA isn't available. The fp16 model was no faster on the 3090. The int8 one was no faster on the CPU. kokoro-onnx was chosen over the PyTorch `kokoro` package to avoid a multi-GB torch install.
- **Piper (fallback):** [piper-tts](https://github.com/OHF-Voice/piper1-gpl) 1.8, voice `en_GB-alan-medium`, always on the **CPU**. Medium voices synthesize a short sentence in ~35 ms on the CPU, but ~100 ms on CUDA, and use no VRAM there. `high` voices (e.g. `en_GB-cori-high`) take ~170 ms per short sentence on the CPU.
- **Fallback:** if Kokoro fails to load (missing files, CUDA error with `device=cuda`, anything else), the server logs a warning and Kokoro voices are spoken with the Piper fallback voice. If Kokoro throws on one sentence, that sentence comes from Piper, also with a warning. If neither engine loads, `build_tts` raises `TTSUnavailableError`.
- **Pitch** is done by resampling: synthesize at `speed / 2^(semitones/12)`, then resample as if recorded at a rate higher by that factor. Duration stays as requested. Formants move too, so keep shifts small (±2 semitones sounds natural).
- **Concurrency:** one synthesis at a time across all streams. Each stream synthesizes ahead in a task (up to 4 segments queued), so later sentences render while earlier audio is being sent.
- **Packaging:** kokoro-onnx and piper-tts depend on the CPU-only `onnxruntime`, which installs the same Python module as `onnxruntime-gpu` and would overwrite it. `[tool.uv] override-dependencies` drops it, and `onnxruntime-gpu` is a base dependency (it also runs on the CPU). Its CUDA 13 / cuDNN libraries come from the `cuda` extra (`onnxruntime-gpu[cuda,cudnn]`) and are loaded with `onnxruntime.preload_dlls()`. They live alongside the CUDA 12 libraries faster-whisper uses. STT and TTS both loaded on CUDA in one process in testing.
- **Models** are files, not Hugging Face cache entries: `scripts/download_tts_models.py` puts them in `ALFRED_TTS_MODEL_DIR` (default `~/.cache/alfred/tts`). The Kokoro model is 310 MB and the voice pack 27 MB. Each Piper medium voice is 60 MB.
- **Loading:** `ALFRED_TTS_ENABLED=true` loads Kokoro (warmed up) and the Piper fallback voice at startup. Other Piper voices load on first use. With TTS disabled, `GET /voices` answers 503.

## Benchmark

`server/scripts/bench_tts.py`, on the RTX 3090 (driver 610.88, Windows 11) and an i7-12700KF, with onnxruntime-gpu 1.31, kokoro-onnx 0.6.1 and piper-tts 1.8. Ollama had `gpt-oss:20b` and the router model resident but idle. Text is streamed word by word into `LocalTTS.synthesize`. **First audio** is from the start of the stream to the first PCM chunk, so it includes splitting, synthesis of the first segment and resampling. Every run uses a different random text: Kokoro on CUDA is about twice as fast on an input it has just seen (~100 ms for a repeated "Good evening, sir."), so a fixed text flatters it. Short = 3–5 words, sentence = 8–12 words, reply = three such sentences. 15 runs each (8 for Kokoro on CPU). CPU is process CPU time per run, summed over all cores.

| Engine | Device | Short: first audio mean / p95 | Sentence: first audio | Reply: first audio / total (9.5 s of audio) | CPU s per reply |
| --- | --- | --- | --- | --- | --- |
| **Kokoro fp32** | **CUDA** | **201 / 213 ms** | 255 / 275 ms | 248 ms / 730 ms | 0.7 |
| Kokoro fp32 | CPU | 412 / 500 ms | 699 / 818 ms | 642 ms / 2.0 s | 23.9 |
| Piper alan-medium | CPU | 38 / 47 ms | 69 / 82 ms | 68 ms / 204 ms | 2.4 |

- **Time to first audio for a short sentence: ~200 ms with Kokoro on CUDA**, inside the ~250 ms target. A 10-word first sentence with no comma is right at ~250 ms. Phonemization takes under 1 ms; the time is model inference.
- **VRAM:** loading Kokoro on CUDA added **~0.75–0.85 GB** (nvidia-smi total, both runs), within the ~5.5 GB ADR 0002 left for TTS. Piper uses none.
- **CPU:** Kokoro on CUDA costs ~0.2 s of CPU per short sentence. Piper is ~0.5 s of CPU per short sentence, spread over cores, so the fallback is cheap enough to run all day.

## Consequences

- The gateway (STU-64) can forward chunks as they arrive. The Android player should expect 24 kHz mono PCM16 regardless of voice.
- Personas (STU-66) pick a `VoiceConfig`. `GET /voices` lists every installed voice per engine with language and gender (gender is Kokoro only).
- The server install now includes onnxruntime-gpu (~250 MB wheel), including in CI. Unit tests use fake engines. The `model`-marked TTS tests skip unless the model files are downloaded.
- Piper is GPL-3.0 (piper1-gpl). Fine for personal use; revisit before distributing the server.
- Follow-ups worth measuring: whether Kokoro's first segment should be capped shorter (e.g. 6 words) to keep long first sentences under 250 ms, and Kokoro latency with the LLM actively generating on the same GPU.
